01

Problem

When a developer opens a pull request, nobody knows how risky the change is until someone reads every line. On a small team, senior developers can't review everything in depth, so risky changes slip through and junior developers' PRs get either rubber-stamped or over-scrutinized at random.

This is a well-studied research problem called just-in-time (JIT) software defect prediction: predicting, at commit time, whether a code change will later be linked to a bug — before it ships, not after.

A model that only outputs 1 or 0 is not enough on its own. Reviewers don't trust a number with no reason behind it, and it gives them nothing to act on. So this system is built to score, explain, and recommend — never just label.

There is no project like this anywhere in the current Batch-10 sheet. The closest entries score network traffic or SOC logs, not source-code diffs.
02

Goals & non-goals

Goals

  • Given a code change (a diff or a Git commit range), output a risk score between 0 and 1.
  • Run entirely on the developer's own machine — no code leaves the laptop.
  • Work the same way on Windows, macOS and Linux.
  • Beat a simple handcrafted-feature baseline with a code-aware model, and prove it with numbers.
  • Never just output a bare risk number — always pair it with a plain-English reason, supporting evidence, and a concrete suggestion.
  • Keep a human in control: the tool recommends, a person decides. Every decision is logged.

Non-goals

  • Not a full CI/CD platform — it scores changes, it doesn't block merges by itself.
  • Not trying to find the exact bug or line — only a risk score at the commit level.
  • Not built for closed-source enterprise codebases with private conventions; trained and evaluated on public open-source data.

04

How it works

git commit / PR diff→ feature extraction→ baseline model + CodeBERT→ weighted risk engine→ RAG evidence + LLM explanation→ reviewer dashboard→ human decision→ audit log

Feature extraction pulls handcrafted signals from the diff and its history: lines added and removed, number of files touched, how scattered the change is, the author's past bug rate, and time since their last commit.

Two models score every change. A logistic regression / random forest baseline runs on the handcrafted features. A fine-tuned CodeBERT model reads the actual code text. The two scores feed a weighted risk engine (see below) so the report can show the code-aware model earns its extra complexity over the simple baseline.

04b

Explain & recommend layer

This is what turns the classifier into a system a reviewer actually trusts and uses — the same shape as CyberShield's SOC platform, pointed at code instead of network traffic.

1. Transparent, weighted risk engine

Instead of one opaque probability, the score is broken into named, weighted signals a reviewer can see at a glance:

SignalExample weight
Large diff, many files touched+25
Touches authentication / payment / core logic+30
Author's historical bug-inducing rate above average+20
No tests added alongside the change+15
CodeBERT semantic score (learned, not handcrafted)blended in

2. RAG evidence retrieval

The system embeds the new diff (using a code-aware embedding model, not a generic text encoder) and searches a curated subset of ApacheJIT's bug-inducing commits — a few thousand, not the full 100k+, to keep the index small enough to bundle and fast enough to demo. A similarity threshold guards against false matches: below it, the system reports plainly that no closely matching historical pattern was found, rather than forcing a match. It surfaces the top matches as concrete evidence — "this change resembles commit X, which introduced bug Y" — the same evidence-citing pattern CyberShield uses with MITRE ATT&CK and CVE data. The index is pre-built once and shipped with the binary, not rebuilt at runtime.

3. LLM explanation, never a verdict

The classifier already decided the score — the LLM's only job is to turn the score, the weighted signals, and the retrieved evidence into two or three plain-English sentences and one concrete suggestion, e.g. "This touches the auth module with no new tests and resembles a past commit that broke login — consider adding a test for the new branch before merging." Runs on Groq's free tier, same as several approved projects on the sheet.

4. Human-in-the-loop + audit log

The tool never blocks a merge by itself. A reviewer sees the score, the explanation, and the evidence, then clicks Approve, Request Changes, or Escalate to senior. Every decision — score, explanation shown, and the human's choice — is written to a local SQLite audit log with a timestamp.

Precision note: scoring and evidence retrieval run fully offline. Only the final explanation sentence calls a cloud LLM (Groq free tier) — and only the risk signals and evidence are sent, never the raw source diff. If that call fails or there's no internet, the score, signal breakdown, and evidence still display; the tool just skips the plain-English sentence rather than failing.

05

Features

  1. Score a single diff or commit range — prscore review HEAD~1 prints a risk score, the weighted signals behind it, and the LLM's plain-English explanation.
  2. Git pre-commit / pre-push hook — runs automatically and warns before a risky change goes out.
  3. Reviewer dashboard (React + TypeScript) — shows score, evidence, explanation, and Approve / Request Changes / Escalate buttons per open PR — this is the demo centerpiece, not an afterthought.
  4. RAG evidence lookup — retrieves and displays the most similar past bug-inducing commits for a given diff.
  5. Batch scan of a repo's history — for the report's evaluation section, and to demo the tool "learning" from a real project.
  6. Local audit log (SQLite) — every score, explanation, and human decision is stored with a timestamp.
06

Training data

ApacheJIT — a public dataset built specifically for just-in-time defect prediction, with over 100,000 labelled commits from major Apache open-source projects. Each commit is already labelled as defect-inducing or clean, using the standard SZZ-algorithm methodology researchers use for this exact task.

This is the one thing that turns this project from "another classifier" into a serious FYP: real, labelled, peer-reviewed-methodology data, not something scraped and self-labelled in a week.

08

Cross-platform packaging

The engine is plain Python, so it doesn't need three separate codebases — it needs three separate builds. PyInstaller (or Nuitka) bundles the Python engine plus the model weights into one native binary per operating system.

GitHub Actions can build all three automatically: a workflow matrix of windows-latest, macos-latest and ubuntu-latest runners each run PyInstaller and upload the binary for that OS. No cross-compiling by hand.

For the FYP demo, the CLI plus a git hook is the strongest "runs locally, works everywhere" story — it's a real developer workflow, not just a web form. A GUI shell (e.g. Tauri, wrapping the same engine) is a stretch goal only if the core scoring and evaluation are already solid.

09

Evaluation

  • AUC-PR (precision-recall, not plain accuracy — defect labels are imbalanced, so accuracy alone would be misleading).
  • Recall at k — the metric that sells this to a non-ML examiner: "if reviewers only check the riskiest 20% of commits by our score, what fraction of all real bugs would they still catch?"
  • Baseline vs. CodeBERT comparison — showing the code-aware model beats the handcrafted-feature baseline, to prove the extra complexity is earned.
  • False-positive rate — a tool that flags everything as risky gets ignored by real teams; this number keeps the tool honest.
  • Explanation quality (qualitative) — a small human-rated sample checking whether the LLM's explanation actually matches the weighted signals and retrieved evidence, so the report can show the explanation layer isn't hallucinating.

11

Risks

Model riskCodeBERT fine-tuning can be noisy on imbalanced defect labels, and free Colab sessions can disconnect mid-run.
Mitigation: class weighting, checkpoint to Google Drive every epoch, train on a curated subset rather than the full dataset, and always keep the simple baseline as a fallback that still works.
Packaging riskPyInstaller builds sometimes miss hidden imports or ship huge binaries — and with only an Ubuntu dev machine, Windows/macOS builds can't be manually tested.
Mitigation: test the Linux build locally in week 3; for Windows/macOS, add a smoke-test step inside the GitHub Actions job itself that runs the built binary on the runner, so a passing CI run is real proof it works.
Data riskApacheJIT is Java-heavy open-source code, not necessarily like a student's own codebase.
Mitigation: state this limitation plainly in the report; optionally test on a second small labelled repo.
Scope riskThe explain/RAG/dashboard layer adds real work on top of the core classifier.
Mitigation: core score + baseline comparison is the non-negotiable deliverable; RAG evidence and the LLM explanation are built next, dashboard last — cut from the bottom if time runs short.
Explanation riskThe LLM could produce an explanation that doesn't match the actual signals (hallucination).
Mitigation: the LLM only rephrases signals and evidence it's given — it never sees the raw diff alone or invents a score — and a small human-rated sample checks this in evaluation.
RAG scale riskEmbedding all 100k+ ApacheJIT commits is too slow and too large for a laptop demo.
Mitigation: embed only a curated subset of bug-inducing commits (a few thousand, from 1–2 projects), not the full dataset.
False-match riskVector search always returns a "closest" result, even when nothing is truly similar.
Mitigation: set a similarity threshold — below it, show "no closely matching historical pattern found" instead of a forced match.
Embedding-model riskA generic text-embedding model doesn't understand code syntax well, producing weak matches.
Mitigation: use a code-aware embedding model (CodeBERT embeddings or a code-tuned embedding model), not a general sentence encoder.
Vector-DB packaging riskChromaDB's local persistence has had cross-OS/version compatibility issues once bundled into a PyInstaller binary.
Mitigation: pin the exact ChromaDB version and test read/write on all three OSes in week 3; keep FAISS (a simpler flat file) as a drop-in backup.
Cold-start riskRebuilding the vector index at runtime bloats install size and slows first launch.
Mitigation: pre-build the index once and ship it bundled with the binary.
Offline-claim riskThe LLM explanation step calls a cloud API, which contradicts an "everything is offline" pitch.
Mitigation: be precise — scoring and retrieval are fully local; only the explanation sentence uses a cloud LLM. Add a local fallback: if the API call fails, still show the score, signals, and evidence without the LLM sentence.
If RAG genuinely doesn't fit the timeline: it's the one layer safe to cut. The weighted risk score, the signal breakdown, and human approve/escalate still stand on their own as a real, explainable system — RAG evidence and the LLM sentence are additive, not load-bearing. Core classifier first, everything above this line is add as time allows, in this order: weighted signals → LLM explanation → RAG evidence → dashboard.
12

Success criteria

  • The CodeBERT model shows a measurable AUC-PR improvement over the handcrafted-feature baseline.
  • Recall-at-20% is reported and clearly explained to a non-technical examiner.
  • Every risk score comes with a weighted signal breakdown, retrieved evidence, and a plain-English explanation — never a bare number.
  • The reviewer dashboard lets a human approve, request changes, or escalate, and every decision is logged.
  • The CLI and git hook run correctly on at least two of the three target operating systems, with build artifacts for all three.
  • The report states data source, methodology, and limitations plainly — no unverified accuracy claims.
